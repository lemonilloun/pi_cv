# Real-time VIO/SLAM для связки Raspberry Pi 5 + Hailo-8 + BNO08x + MacBook M2 (июль 2026)

## TL;DR
- **Берите классическую геометрическую VI-SLAM, а не нейросетевую.** Для монокуляр+IMU без LiDAR на связке «Pi 5 + компаньон-Mac» единственный практичный путь в июле 2026 — зрелые оптимизационные/фильтровые системы: **ORB-SLAM3** (полный VI-SLAM с loop closure) либо связка **OpenVINS/VINS-Fusion (фронтенд-одометрия) + maplab/pose-graph бэкенд** для глобальной согласованности. Нейросетевые DROID-SLAM/DPVO/DPV-SLAM требуют дискретной NVIDIA CUDA GPU и на Pi 5 (нет CUDA) не работают, а на Mac M2 (CUDA отсутствует в принципе) — максимум частично и медленно.
- **Pi 5 CPU не тянет полноценный VI-SLAM в реальном времени на 20–30 FPS.** По независимым замерам (SMF-VO, arXiv:2511.09072, ноябрь 2025) на Pi 5 (quad-core 2.4 ГГц Cortex-A76, без GPU): ORB-SLAM3 ~65 мс/кадр в стерео (только трекинг) → ~15 FPS, VINS-Fusion ~51 мс → ~19 FPS, OpenVINS ~43 мс → ~23 FPS. Рекомендуется гибрид: Pi ведёт лёгкий фронтенд + IMU-преинтеграцию, а тяжёлый бэкенд (BA, loop closure, pose-graph) уносится на M2 по сети — это признанный паттерн edge-offloading SLAM.
- **Два прерэквизита обязательны до любого VIO:** (1) переключить BNO08x в SHTP и получать сырые gyro+accel (лучше по SPI, чтобы обойти нестандартный I2C clock-stretch у BNO08x), в идеале ≥200 Гц по гироскопу; (2) провести камера-IMU калибровку (Kalibr) — обязательно учтя, что Camera Module 3 построена на сенсоре **Sony IMX708 с rolling shutter**, что нарушает допущения о global shutter, встроенные в большинство VIO-систем.

## Key Findings
- **VIO ≠ VI-SLAM.** VIO (одометрия) даёт локально точную траекторию, но накапливает дрейф и не имеет глобальной согласованности; VI-SLAM добавляет распознавание мест (loop closure) + оптимизацию графа поз/BA и даёт единую согласованную карту. Пользователю нужен именно **VI-SLAM**, поскольку цель — настоящая карта, а не дрейфующее счисление пути.
- **ORB-SLAM3** — эталон точности и, по формулировке авторов (Campos, Elvira, Gómez Rodríguez, Montiel, Tardós, *IEEE Transactions on Robotics* 37(6):1874–1890, дек. 2021), «первая система, способная выполнять визуальный, визуально-инерциальный и мультикарточный SLAM с монокулярными, стерео и RGB-D камерами, используя пинхол- и fisheye-модели объектива». Единственная зрелая open-source система, делающая полный монокуляр-инерциальный VI-SLAM с loop closure «из коробки»: feature-based (ORB), граф-оптимизация (g2o), BA, мультикарты Atlas, релокализация. Есть форки под Raspberry Pi 5 (ARM) и порт под macOS.
- **VINS-Fusion / VINS-Mono** (HKUST) — оптимизационная VIO с опциональным loop closure и pose-graph, поддержка mono+IMU. Backend часто искусственно ограничивают ~10 Гц из-за нагрузки CPU; очень тяжёлая по CPU.
- **OpenVINS** — MSCKF (фильтровая) VIO, легче оптимизационных, с онлайн-калибровкой экстринсики и таймофсета камера-IMU; loop closure только через вторичный слабосвязанный поток / экспорт в maplab. По сути это одометрия, глобальную согласованность нужно добавлять снаружи.
- **Basalt** — оптимизационная VIO с локальным BA и глобальной pose-graph оптимизацией/мэппингом через non-linear factor recovery; очень эффективна по CPU (на Pi 5 ~24 мс/кадр → ~42 FPS в стерео-VO). Требует стерео/хорошей калибровки, менее «дружелюбна» в настройке.
- **Kimera(-VIO)** — VIO (на GTSAM) + robust pose graph optimization (RPGO) + 3D mesh + семантика; работает в реальном времени на CPU (на десктопе), но ориентирована на стерео+IMU и тяжелее в сборке.
- **RTAB-Map** — граф-SLAM с loop closure (bag-of-words), отлично пакетирован под ROS2, но исторически заточен под RGB-D/стерео/LiDAR; для чистого монокуляр+IMU это не первый выбор.
- **Cartographer** — LiDAR-ориентированный, для camera+IMU не подходит; исключаем.
- **Нейросетевые VO/SLAM** (DROID-SLAM, DPVO, DPV-SLAM; новые 2025/2026 — VINGS-Mono, FoundationSLAM (AAAI 2026), ViPE (NVIDIA)) — высокая точность/робастность, но GPU-центричны. DPV-SLAM (Lipson, Teed, Deng, ECCV 2024) «работает на 1x–4x реального времени» на одной GPU при 5–7 ГБ VRAM (на KITTI — 39 FPS); ViPE (NVIDIA Research, 11 авг. 2025) — «3–5 FPS на одной GPU» при 640×480 на RTX 5090. На Pi 5 без CUDA не запускаются.
- **SMF-VO (2025)** — новейшая сверхлёгкая «motion-centric» VO, «более 100 FPS на Raspberry Pi 5 при использовании только quad-core 2.4 ГГц CPU», но это чистая одометрия: по признанию авторов и обзора, метод «обходит явную оценку позы и дорогое отслеживание landmark'ов» и «ограничен отсутствием loop closure» — задачу глобальной карты не решает.

## Details

### 1. Состояние SOTA камера+IMU SLAM/VIO на середину 2026

**Классические/геометрические системы (то, что реально используют практики):**

| Система | Вход | Loop closure + PGO + BA | Категория | Real-time на Pi 5 CPU | Зрелость |
|---|---|---|---|---|---|
| **ORB-SLAM3** | mono/stereo/RGB-D (+IMU) | Да (полный VI-SLAM, Atlas) | VI-SLAM | ~65 мс/кадр → ~15 FPS (стерео, только трекинг) — не тянет 20–30 FPS | Очень высокая, эталон точности |
| **VINS-Fusion/Mono** | mono/stereo +IMU | Да (loop closure + PGO, опц.) | VIO→VI-SLAM | ~51 мс → ~19 FPS; backend часто throttled до ~10 Гц | Высокая, широко применяется |
| **OpenVINS** | mono/stereo +IMU | Нет в ядре (вторичный LC/maplab) | VIO (MSCKF) | ~43 мс → ~23 FPS (легче прочих) | Высокая, эталон фильтров |
| **Basalt** | stereo +IMU | Да (local BA + global PGO) | VIO+mapping | ~24 мс → ~42 FPS (стерео-VO) — самая лёгкая | Высокая, но капризна |
| **Kimera-VIO** | stereo +IMU | Да (RPGO) + 3D mesh + семантика | VI-SLAM | Real-time на CPU (десктоп); на Pi тяжело | Высокая |
| **RTAB-Map** | RGB-D/stereo/LiDAR (+IMU) | Да (BoW LC + graph opt) | Graph-SLAM | Зависит от сенсора; для mono+IMU слабо | Высокая, отличный ROS2-пакет |
| **OKVIS2** | stereo +IMU | Да | VI-SLAM | ~128 мс → ~8 FPS на Pi 5 — тяжёлая | Средняя-высокая |
| **Cartographer** | LiDAR (+IMU) | Да | LiDAR-SLAM | Неприменимо (нет LiDAR) | Высокая, но не по профилю |

**Нейросетевые / обучаемые (новое, но GPU-зависимое):**
- **DROID-SLAM** — плотный BA на recurrent-сети; высокая точность/робастность, требует мощной GPU и много VRAM.
- **DPVO / DPV-SLAM (Princeton, NeurIPS 2023 / ECCV 2024)** — «Deep Patch» разреженная VO/SLAM; DPV-SLAM добавляет loop closure, работает на одной GPU (1x–4x реального времени, 5–7 ГБ VRAM).
- **Новое 2025/2026:** VINGS-Mono (Gaussian-splatting монокуляр-инерциальный SLAM, серверная обработка ~1–2 FPS), FoundationSLAM (AAAI 2026, использует depth foundation models), ViPE (NVIDIA, 3–5 Гц на RTX 5090), 360DVO (RAL 2026). Все GPU-центричны, для исследований, не для edge-CPU.
- **SMF-VO (arXiv:2511.09072, 2025)** — 100+ FPS на Pi 5 CPU, но чистая одометрия без карты/loop closure.

**Вывод по SOTA:** «Что реально используют практики» на середину 2026 для camera+IMU без LiDAR — это по-прежнему **ORB-SLAM3, VINS-Fusion, OpenVINS, Basalt, Kimera**. Нейросетевые системы — горизонт исследований и приложения с дискретной GPU; выдавать их за готовое edge-решение неверно.

### 2. Реализуемость на данном железе

**(a) Что идёт на Pi 5 CPU в реальном времени** (Pi 5, 2.4 ГГц quad-core Cortex-A76, без GPU; SMF-VO arXiv:2511.09072):
- ORB-SLAM3: ~65 мс/кадр (стерео, EuRoC), ~72–80 мс (TUM-VI) → 12–15 FPS, и это **только трекинг без препроцессинга и без потоков мэппинга/loop closure**; полноценно 20 Гц-камеру Pi 5 не держит.
- VINS-Fusion: ~51 мс/кадр → ~19 FPS, но точность на Pi 5 хуже ORB-SLAM3, CPU-нагрузка высокая (порядка 5 ядер по данным KTH-диссертации).
- OpenVINS: ~43 мс/кадр (TUM-VI) → ~23 FPS, легче прочих (MSCKF, линейная сложность).
- Basalt: ~24 мс/кадр → ~42 FPS (стерео-VO) — самый лёгкий «полноценный» вариант.
- OKVIS2: ~128 мс → ~8 FPS — слишком тяжёлая.
- SMF-VO: ~8 мс/кадр → 100+ FPS (но без loop closure).

Практический вывод: **монокуляр-VIO фронтенд** (трекинг + IMU-преинтеграция) реалистично гонять на Pi 5 в районе 15–30 FPS, но **глобальную оптимизацию (BA/loop closure) на Pi 5 в реальном времени параллельно тянуть тяжело**, тем более что Hailo-8 уже занят YOLOv8-seg + CLIP. Важно: **Hailo-8 — NPU для нейросетевого инференса, он НЕ ускоряет геометрический SLAM** (ORB/оптический поток/BA идут на ARM CPU).

**(b) Гибрид «фронтенд на Pi, бэкенд на Mac» — рекомендуемый паттерн.** Edge-offloading SLAM — известная рабочая архитектура: тайминг-критичные Tracking + Local Mapping на устройстве, а Loop Closing + Global BA — на сервере (схема AdaptSLAM). Существуют распределённые обёртки поверх монокулярного ORB-SLAM3 на **ROS2 + FastDDS**. Латентный бюджет: фронтенд-одометрия должна отдавать позу локально с задержкой единицы–десятки мс (для управления роботом), а бэкенд-коррекции (loop closure) могут приходить с задержкой сотни мс–секунды — они не в контуре управления, лишь исправляют карту/дрейф. Протоколы: **ROS2 DDS** (штатно для SLAM-нод), либо кастомный **TCP/ZeroMQ/UDP** для сырых потоков (изображения/фичи/IMU). VGA-кадр при 8 бит/пиксель передаётся за ~3 мс по быстрому линку; узкое место — вычисления, не сеть.

**(c) macOS/Apple Silicon бэкенд.** ORB-SLAM3 имеет неофициальный порт под macOS (royshil/ORB_SLAM3_macosx: правки CMakeLists/build.sh и кода). Но большинство SLAM-стеков нативно живут в Linux/ROS. **Практичнее** запускать бэкенд на M2 в Docker/Linux-контейнере (arm64) или Ubuntu-VM, а не бороться с нативной сборкой под macOS. CUDA на Mac нет вообще — любые нейросетевые CUDA-SLAM на M2 не пойдут.

### 3. Переключение BNO08x в SHTP и сырые IMU-данные

- **BNO08x = BNO085/BNO086**: акселерометр, гироскоп, магнитометр + Cortex-M0+ с прошивкой CEVA SH-2; поддерживает I2C, SPI, UART. UART-RVC (текущий режим) — упрощённый, только фьюженные yaw/pitch/roll + accel; для сырых данных нужен **SHTP** по I2C/SPI/UART-SHTP.
- **Интерфейс: рекомендуется SPI.** BNO08x использует **нестандартный clock-stretching по I2C**, нарушающий протокол и вызывающий сбои/таймауты (ETIMEDOUT), особенно на высоких rate; SPI этого лишён и быстрее (SPI ~40% быстрее I2C и в разы быстрее UART). Для SPI на большинстве breakout нужно перемкнуть PS1 (солдер-бридж) и подключить INT + RESET + WAKE(PS0).
- **Если всё же I2C:** поднять частоту до 400 кГц (`dtparam=i2c_arm_baudrate=400000`), при необходимости software-I2C (`i2c-gpio` overlay) для обхода clock-stretch, неравные подтяжки (~1К на SDA, 4.7К на SCL). Обязательно INT и RESET.
- **Rate:** для VIO нужен гироскоп ≥200 Гц. SH-2 обещает до 400 Гц фьюжн; сырые accel+gyro на 200 Гц читаются (подтверждено на MCU). **Подводные камни:** (1) магнитометр обновляется медленнее прочих отчётов независимо от rate (datasheet 6.9 Report Rates), для VIO он и не нужен; (2) при нескольких одновременных отчётах суммарная частота падает — виновата коммуникационная прошивка BNO08x; (3) **Adafruit CircuitPython BNO08x на Pi часто ограничивает ~20 отчётов/с** и работает медленно — для 200 Гц Python-драйвер Adafruit, скорее всего, **не подойдёт**, нужен C/SPI-драйвер; (4) сырой accel (0x14) отдаёт «сырые ADC-единицы» и требует своей калибровочной функции — для VIO берите калиброванные accel (0x01, м/с²) и калиброванный gyro; (5) BNO08x округляет запрошенный report interval к фиксированным значениям, возможен джиттер — опирайтесь на аппаратный таймбейс отчёта, а не время прихода на хосте.
- Существует ROS2-драйвер **`bno08x_driver`**, явно поддерживающий SHTP (и предупреждающий, что UART-RVC не поддерживается) — удобно для ROS2-пути.

### 4. Камера-IMU калибровка (обязательный прерэквизит)

- **Стандартный инструмент — Kalibr (ethz-asl)**: интринсики мультикамер, **пространственно-временная камера-IMU калибровка** (экстринсика + таймофсет + интринсики IMU), IMU-IMU и **калибровка rolling-shutter камер** (модель `pinhole-radtan-rs`, оценка line delay). Таргеты — AprilTag.
- **Camera Module 3 — rolling shutter.** Модуль построен на «Sony IMX708 12 Мп, 4608×2592» с back-illuminated stacked CMOS; по документации Raspberry Pi это rolling-shutter сенсор («сканирует изображение построчно»), в отличие от их же Global Shutter Camera на IMX296 (1456×1088). Camera Module 3 пишет Full HD 50 fps (выше fps — на меньшем разрешении), DFOV 75° (или 120° Wide). Это важно: базовый Kalibr camera-IMU и большинство VIO (ORB-SLAM3, VINS, стандартный OpenVINS) неявно рассчитаны на **global shutter**; rolling shutter вносит построчный сдвиг времени, портящий калибровку и оценку позы при быстром движении/вращении. Пути: (1) rolling-shutter расширение Kalibr для оценки line delay и подача его в RS-совместимую систему (OpenVINS имеет модель rolling shutter); (2) минимизировать эффект — высокая выдержка/меньшее разрешение, ограничение скорости движения; (3) новые continuous-time RS-калибраторы (2022+). Для монокуляр+IMU это заметный риск-фактор.
- **Порядок:** сначала интринсики камеры (+RS line delay) → затем camera-IMU экстринсика/таймофсет с шумовыми параметрами IMU (noise density / random walk из даташита BNO08x как стартовые).

### 5. Единый рекомендуемый путь для передачи кодинг-агенту

**Основная рекомендация: ROS2 (Humble/Jazzy) как каркас + ORB-SLAM3 (mono-inertial) как первичная VI-SLAM-система, с гибридным разнесением при нехватке производительности.**

Обоснование: ORB-SLAM3 — единственная зрелая система, дающая монокуляр-инерциальный VI-SLAM с loop closure «из коробки», есть ARM/Pi-форки и macOS-порт; ROS2 даёт готовые обёртки, DDS-транспорт и путь к navigation stack. Если Pi 5 не потянет полный ORB-SLAM3 в реальном времени — план B: **OpenVINS (лёгкий MSCKF-фронтенд на Pi) + maplab/pose-graph бэкенд на M2** для глобальной согласованности.

Поэтапно (для плана, который построит агент):
1. **IMU:** BNO08x → SHTP по SPI, C-драйвер, сырые calibrated gyro+accel ≥200 Гц, публикация в ROS2 `sensor_msgs/Imu` с корректными таймстемпами.
2. **Камера:** Camera Module 3 через libcamera → ROS2 image topic, фиксированные экспозиция/усиление, известное разрешение/FPS.
3. **Калибровка:** Kalibr — интринсики (+ rolling-shutter line delay) и camera-IMU экстринсика/таймофсет.
4. **Синхронизация времени** камера↔IMU (общий монотонный таймбейс, аппаратный таймстемп IMU-отчёта).
5. **VI-SLAM v1:** ORB-SLAM3 mono-inertial на Pi 5, замер FPS/дрейфа/успешности loop closure.
6. **Если не тянет:** разнести — Pi гонит фронтенд (трекинг + IMU-преинтеграция) и стримит фичи/ключевые кадры + IMU по ROS2 DDS/ZeroMQ на M2; M2 (Docker/Linux arm64) держит бэкенд (local/global BA, loop closure, карта). Либо OpenVINS-на-Pi + maplab-на-Mac.
7. **Карта/навигация:** экспорт согласованной траектории/карты, стыковка с существующими TSDF/Open3D и scene graph по потребности.

Standalone C++/Python против ROS2: standalone проще для одиночного бинарника ORB-SLAM3, но для распределённого фронтенд/бэкенд и будущей навигации **ROS2 практичнее** (готовый транспорт, тайм-синхронизация, экосистема). Рекомендуется ROS2.

### 6. VIO против VI-SLAM (что к какой категории относится)
- **Чистая VIO (дрейф, без глобальной карты):** OpenVINS (ядро), Basalt-VIO (без mapping-модуля), ROVIO, MSCKF, SMF-VO, DPVO, большинство обучаемых VO. Хороши как локальная одометрия/фронтенд.
- **Полный VI-SLAM (loop closure + глобальная согласованность):** ORB-SLAM3, VINS-Fusion (с включённым loop closure + pose-graph), Kimera (VIO+RPGO), Basalt (с mapping/NFR), RTAB-Map, DROID-SLAM/DPV-SLAM (нейро).
- Пользователю нужен **VI-SLAM** → либо система из второй группы целиком, либо VIO из первой + отдельный слой loop closure/pose-graph (maplab поверх OpenVINS/VINS).

## Recommendations
1. **Сначала прерэквизиты (1–2 недели):** BNO08x → SHTP/SPI, сырые gyro+accel ≥200 Гц; Camera Module 3 через libcamera с фиксированной экспозицией; Kalibr-калибровка с учётом rolling shutter. Без этого любой VIO будет нестабилен.
2. **Первичная система — ORB-SLAM3 mono-inertial под ROS2** на Pi 5. Бенчмаркать реальные FPS и качество loop closure. Порог перехода к плану B: устойчиво <10–12 FPS трекинга или срываются инициализация/loop closure.
3. **План B (гибрид):** фронтенд на Pi + бэкенд на M2 (Docker/Linux) по ROS2 DDS; либо OpenVINS-Pi + maplab-Mac. Порог успеха: локальная поза ≥20 Гц с задержкой <50 мс, коррекции карты <1 c.
4. **Не тратить время на нейросетевые CUDA-SLAM** (DROID/DPVO/DPV-SLAM/ViPE/FoundationSLAM) на этом железе — нет CUDA ни на Pi, ни на Mac. Пересмотреть только при появлении дискретной NVIDIA GPU.
5. **Rolling shutter — держать под контролем:** ограничить скорость/вращение робота на первых итерациях, оценить line delay, при возможности выбрать VIO с RS-моделью (OpenVINS).
6. **Hailo-8 не переиспользовать под SLAM** — он занят YOLO/CLIP и не ускоряет геометрию; SLAM живёт на ARM CPU (Pi) и на M2.

## Caveats
- Точные FPS ORB-SLAM3 именно в mono-inertial на Pi 5 из целевой статьи (Eshan & Lav, «An In-depth Evaluation of ORB-SLAM3 on the Raspberry Pi 5», IEEE Access 2025) подтвердить прямой цитатой не удалось (страница отдавала HTTP 429). Приведённые числа — из независимого источника SMF-VO (arXiv:2511.09072, 2025), где ORB-SLAM3 замерялся в **стерео-режиме и только по времени трекинга** (без препроцессинга и потоков мэппинга), т.е. реальные end-to-end показатели ниже. Монокуляр-режим может быть легче стерео.
- Числа CPU-нагрузки (VINS-Mono ~521%, OpenVINS ~323% от одного ядра) — из магистерской диссертации KTH, не из рецензируемой статьи; трактовать как порядок величины.
- «Basalt Python VIO 2026» из блога johal.in содержит маркетинговые/спекулятивные утверждения («80% edge-VIO», «quantum-accelerated BA») — не подтверждено, как факт не использовано.
- Реальная достижимость параллельного full-BA + loop closure на M2 через сеть зависит от качества линка и реализации; это инженерный риск, требующий прототипирования.
- Depth Anything V2 (единственный источник глубины «живой карты») для монокуляр-VIO не требуется — масштаб даёт IMU, — но метрический масштаб монокуляр-инерциальной инициализации чувствителен к возбуждению движения (нужно достаточное ускорение/вращение при старте).
